# TOTP Two-Factor Authentication Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An HR admin can enroll an authenticator app, and every later login for that user requires a valid 6-digit TOTP code; another HR admin can reset a locked-out user's 2FA.

**Architecture:** A pure RFC 6238 module in `talentos-authz` generates secrets and verifies codes. The gateway stores the secret encrypted with the existing `PiiCipher` on `users`, gates password login on it, and exposes enroll/enable/disable plus an admin reset. The `/settings` page gets a security card and the login page asks for a code only after the gateway answers `totp_required`.

**Tech Stack:** Rust/Axum/SQLx, `hmac` + `sha1` + `base32` (new workspace deps), existing `PiiCipher`, Next.js 15, Playwright (Node `crypto` computes the code in the E2E).

**Spec:** `docs/superpowers/plans/2026-10-27-competitive-gap-roadmap.md` (Phase 3 item 6: 2FA for HR admins; continuous trust work).

## Global Constraints

- TOTP secrets are never returned after enrollment and never logged; at rest they are encrypted with `PII_ENCRYPTION_KEY`.
- Secrets are 20 random bytes, base32 (no padding), 6 digits, 30-second period, ±1 step skew.
- Password verification still runs before the TOTP check; a wrong code returns 401 `invalid_totp`; a missing code for an enabled user returns 401 `totp_required`.
- Login/refresh rate limits stay in force; audit every enroll/enable/disable/reset.
- Revoke the target user's refresh tokens on disable and on admin reset.
- No `unwrap()`/`expect()` in production; no plaintext secret in responses or audit.
- Existing users without 2FA keep working unchanged; setup requires `PII_ENCRYPTION_KEY` (503 with a clear message when unset).
- Thai UI, existing classes; `cargo fmt/clippy/test`, `npm run build`, Playwright 12/12.

## Review Focus

- **No bypass:** an enabled user cannot log in with password only, an empty code, a code from the wrong secret, or a code outside the ±1 step window.
- **Secret handling:** the setup response is the only time the secret leaves the server; DB and audit rows contain ciphertext/no secret.
- **Lockout recovery:** an HR admin can reset another user's 2FA; the reset revokes that user's sessions and audit-logs the actor.
- **Key missing:** setup fails closed (503) rather than storing a plaintext secret.
- **Disabled user:** disabling requires a valid current code and drops 2FA immediately.
- **Replay/timing:** codes are compared without early-exit string equality; the same code outside the window is rejected.

```rust
// talentos-authz::totp
pub fn generate_secret() -> String;                       // base32, 20 bytes
pub fn otpauth_url(account: &str, secret: &str) -> String; // issuer TalentOS
pub fn verify(secret_b32: &str, code: &str, unix_seconds: u64) -> bool; // ±1 step
pub fn code_at(secret_b32: &str, step: u64) -> Option<String>; // tests/e2e helpers

// Gateway
// POST /api/v1/auth/2fa/setup   (authed) -> {secret, otpauth_url}; 409 if enabled; 503 if no PII key
// POST /api/v1/auth/2fa/enable  {code} -> {totp_enabled:true}; 400 bad code
// POST /api/v1/auth/2fa/disable {code} -> {totp_enabled:false}; 400 bad code
// POST /api/v1/users/:id/2fa/reset (user_management.reset_2fa) -> {totp_enabled:false}
```
- Migration: `users.totp_secret TEXT`, `users.totp_enabled BOOLEAN NOT NULL DEFAULT FALSE`, `users.totp_enabled_at TIMESTAMPTZ`.
- Login body gains `totp_code: Option<String>` (6 digits when present).
- `authenticate` selects `totp_secret, totp_enabled` via the BYPASSRLS pool, decrypts with `state.pii`, and enforces the gate after the password check.
- Disable and reset revoke the user's refresh tokens and write `audit_log` rows (`auth.2fa_*`, `user.2fa_reset`).

**Interfaces:** consumes Task 1 endpoints and login error codes.

- Settings card “ความปลอดภัย (2FA)”: shows enabled/disabled; “ตั้งค่า 2FA” fetches the secret, displays it plus the `otpauth://` URI for manual entry, code input `totp-enable-code`, confirm `enable-2fa`; when enabled, “ปิด 2FA” with code input `totp-disable-code`, confirm `disable-2fa`, and a note that HR can reset it.
- Login: when the response `error === "totp_required"`, reveal a code input `login-totp`, focus it, and resend with `totp_code`; `invalid_totp` shows a Thai error and keeps the field.
- Users page: for each active user with 2FA (or always), a button `reset-2fa` (hr_admin) with a confirm dialog; success notice.
- E2E test 12: HR enables 2FA (read the displayed secret, compute the current code with Node `crypto.createHmac("sha1", ...)`), logs out, logs in again with password → code field appears → enters a fresh code → lands on the dashboard; then disables 2FA using a fresh code so the suite stays replayable.
